# V0.8 — Scheduling, status, owner-only IPC and Windows desktop

Status: partial V0.8, 2026-11-18. The scheduler/status core, one-shot ticks,
versioned owner-only local IPC and a Windows C# desktop shell are implemented.
The desktop can run status/tick and repository capture/history/verify/restore/
retention-preview through the same core. OS scheduler installers, platform secret
store integration, quota/restart/clock qualification, accessibility testing and
independent-operator evidence remain open. This is not a supported release.

## Core commands

```text
peervault schedule-status --config <jobs.json> --state <state.json>
peervault schedule-tick   --config <jobs.json> --state <state.json>
peervault agent --endpoint <pipe-name-or-unix-socket>
```

`status` is read-only and reports freshness per job. `tick` executes at most one
run for each due enabled job, then atomically replaces the state file. An
OS-owned file lock prevents two ticks; process death releases ownership and there
is no age-based stale-lock clearing. The scheduler remains a one-shot command; use
the OS scheduler, not an in-process daemon.

## Owner-only IPC

Windows uses a named pipe. Linux uses an absolute Unix-domain socket path. No TCP
port is opened. The server accepts one newline-delimited JSON request per
connection and replies with one JSON line.

Request:

```json
{
  "schema_version": 1,
  "request_id": "history-1",
  "argv": ["history", "--repository", "D:\\vault\\repository", "--backend", "D:\\tools\\restic.exe", "--password-file", "D:\\secrets\\vault.txt"]
}
```

Response:

```json
{
  "schema_version": 1,
  "request_id": "history-1",
  "result": "pass",
  "exit_code": 0,
  "report": { "schema_version": 2, "result": "pass", "snapshots": [] }
}
```

`report` is the core's normal JSON document. On failure the core runs with the
global `--error-json` flag, so `report` contains `{code, message}` and `error`
repeats the message. The agent never receives a password value; it forwards only
a `--password-file` path.

Allowlisted top-level operations: `init`, `capture`, `history`, `verify`,
`restore`, `recovery-kit`, `retention`, `schedule-status`, `schedule-tick`.
`agent`, R0 fixture/bakeoff commands and copy drills are not exposed.

### Permission boundary

- Windows: the pipe is created by the core and each accepted client's process
  token user SID is compared with the server token user SID. A different user is
  disconnected. The default pipe DACL is supplemented by this explicit check.
- Linux: the socket must live in a directory that is not group/other writable,
  the socket is mode `0600`, and `SO_PEERCRED` UID must equal the socket owner.
- A same-account process is not excluded by this boundary. The core remains the
  sole mutation authority because the agent executes the core binary rather than
  mutating repository state itself.
- Requests are bounded to 64 KiB, 64 arguments of 4 KiB, and 1 hour/16 MiB of
  child output. The IPC agent has no listening network endpoint.

## Job configuration

```json
{
  "schema_version": 1,
  "jobs": [
    {
      "id": "daily-verify",
      "kind": "verify",
      "repository": "D:\\vault\\repository",
      "backend": "D:\\tools\\restic.exe",
      "password_file": "D:\\secrets\\vault.txt",
      "interval_seconds": 86400,
      "freshness_seconds": 172800
    },
    {
      "id": "weekly-scratch-restore",
      "kind": "restore",
      "repository": "D:\\vault\\repository",
      "backend": "D:\\tools\\restic.exe",
      "password_file": "D:\\secrets\\vault.txt",
      "snapshot": "<snapshot-id>",
      "destination_root": "D:\\vault\\scratch",
      "interval_seconds": 604800,
      "freshness_seconds": 1209600
    }
  ]
}
```

- `verify` performs the existing repository full read; `snapshot` may pin the
  existence assertion.
- `restore` creates a new timestamped destination under `destination_root/<id>/`.
  It never reuses or overwrites a target. `minimum_free_bytes` refuses a scratch
  restore before creating a destination when the target has insufficient space.
- `password_file` is optional. When omitted, the core reads
  `PEERVAULT_PASSWORD_FILE` (for example a systemd `LoadCredential` path) or
  `PEERVAULT_PASSWORD`; a scheduled job with neither is refused.
- Job commands run through the same bounded process runner as the CLI. Password
  material is never copied into state.
- The state file records last attempt/success, result, destination, next due,
  missed-run count, consecutive failures and clock anomalies. It contains no
  password or file contents.
- On Unix the state file is set to `0600`; Windows owner ACL provisioning remains
  an installer/task responsibility.

## Scheduling

Linux example:

```text
*/15 * * * * /usr/local/bin/peervault schedule-tick --config /etc/peervault/jobs.json --state /var/lib/peervault/state.json
```

Use a dedicated account, a `0700` state directory and an owner-only `0600`
password file. A systemd timer can replace cron; the same owner/lock rules apply.
Windows Task Scheduler should run the same command under one documented task
identity. Do not put the password on the command line.

Installers:

```text
# Windows, current user, S4U (no stored password), every 15 minutes
powershell -File scripts/install-scheduler.ps1 -Core <peervault.exe> -Config <jobs.json> -State <state.json>
powershell -File scripts/uninstall-scheduler.ps1

# Linux, user-level systemd timer with a systemd credential, every 15 minutes
bash scripts/install-scheduler.sh --core <peervault> --config <jobs.json> --state <state.json> \
  --credential /owner-only/secret.txt --every 15min
bash scripts/uninstall-scheduler.sh
```

Both run `schedule-tick`, not an in-process daemon. The scheduler unit/action
never contains the password value.

- Linux: `--credential` adds `LoadCredential=peervault:<source>` and
  `Environment=PEERVAULT_PASSWORD_FILE=%d/peervault`. The source must be
  owner-only; the job config may omit `password_file`.
- Windows: `scripts/secret-store.ps1 -Action Store` protects the secret with
  current-user DPAPI. `install-scheduler.ps1 -ProtectedSecret <file>` runs
  `task-run.ps1`, which decrypts to an explicit owner-only ACL file in a random
  per-run path under `%LOCALAPPDATA%\PeerVault\run`, runs one tick, and removes
  it. The job config may omit `password_file`. Same-user DPAPI and S4U task
  identity remain environment-specific; test the exact task account.
- Linux units omit `ProtectHome` because a repository may live under the owner's
  home; use a dedicated account and owner-only paths.

## Windows desktop

`desktop/PeerVault.Desktop` is a .NET 10 WinForms shell. Build it with:

```text
dotnet build desktop/PeerVault.Desktop/PeerVault.Desktop.csproj -c Release
```

The desktop starts the core `agent` on a random GUID pipe name, verifies the
connected pipe server PID equals the spawned agent before trusting any response,
and exposes:

- scheduler status and due-job tick;
- capture, history, verify and restore;
- retention preview against the owner state.

All operations are JSON through the same IPC contract; the desktop does not
mutate repository state directly. It does not yet edit source policy or job
configuration, inspect copy/conflict state, or perform retention apply. Recovery
instructions are still read from `docs/`.

## Verified in this slice

`scripts/v08-ipc.py` on Windows/NTFS and Ubuntu 22.04/WSL2:

- a same-user named-pipe/Unix-socket request returned `history`;
- an unsupported operation and a wrong schema version were refused;
- an unknown request field was refused;
- a missing password reference returned the core's JSON failure;
- `schedule-status` returned the expected `unknown` job status;
- a second agent could not own the same endpoint;
- the endpoint restarted and served again;
- the desktop refuses a pipe whose server PID is not its spawned agent (code
  path; the C# build passes).

`scripts/v08-schedule.py` additionally verified `unknown` → `fresh`, no re-run
when not due, missed-run counting, clock-anomaly skip, credential-file
environment delivery, refusal while another process holds the OS lock and
successful resume after that process exits, free-space refusal before creating a
restore destination, and a successful scratch restore after the quota was
relaxed.

`scripts/v08-secret.py` stored a repository secret with current-user DPAPI,
removed the plaintext, ran a job through `task-run.ps1` with no `password_file`,
and confirmed the runtime secret was deleted. Cross-user denial needs a second OS
account and is not covered by these drills.

## Not implemented / not qualified

- Scheduler installers and the DPAPI/systemd-credential paths exist, but a
  different task account, cross-user denial, service-account provisioning and
  Credential Manager/systemd-credential expiry are not independently qualified.
- No recovery/access-change/key-migration runbook inside the desktop.
- Free-space preflight exists for scheduled scratch restores; output-retention
  policy, cancellation surface, restart reconciliation with a backend journal and
  real clock/storage stress remain open.
- No keyboard/screen-reader qualification of the restore/recovery path.
- No second-operator usability run or independent hardware evidence.
- No retention apply or remote-peer operation over IPC; preview only.
- Unit tests cover schedule selection/classification/missed/clock logic; drills
  cover a real scheduled subprocess, credential delivery and quota refusal.
  Reboot/suspend, other task identities, physical disk-full and clock/storage
  stress remain untested.
