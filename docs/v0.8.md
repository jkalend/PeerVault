# V0.8 — Scheduler/status core (experimental)

Status: partial V0.8 implementation, 2026-11-03. The scheduler/status core,
owner-only local stdio agent and a thin Windows C# status/tick desktop are
implemented. The versioned named-pipe/Unix-socket contract, full desktop
operations, OS scheduler installers, secret delivery and the restart/clock/
cadence qualification matrix remain open. This is not a supported scheduling or
desktop release.

## Commands

```text
peervault schedule-status --config <jobs.json> --state <state.json>
peervault schedule-tick   --config <jobs.json> --state <state.json>
peervault agent           --config <jobs.json> --state <state.json>
```

`status` is read-only and reports freshness per job. `tick` executes at most one
run for each due enabled job, then atomically replaces the state file. A second
tick refuses while the owner lock exists; stale locks are never cleared by age.
`agent` serves newline-delimited `status`/`tick` requests over inherited
stdin/stdout: only the owning desktop parent can reach it. This is an owner-only
anonymous-pipe boundary, not the final versioned named-pipe/Unix-socket contract.

## Job configuration

```json
{
  "schema_version": 1,
  "jobs": [
    {
      "id": "daily-verify",
      "kind": "verify",
      "repository": "D:\\vault\\repository",
      "backend": "D:\\tools\\restic.exe",
      "password_file": "D:\\secrets\\vault.txt",
      "interval_seconds": 86400,
      "freshness_seconds": 172800
    },
    {
      "id": "weekly-scratch-restore",
      "kind": "restore",
      "repository": "D:\\vault\\repository",
      "backend": "D:\\tools\\restic.exe",
      "password_file": "D:\\secrets\\vault.txt",
      "snapshot": "<snapshot-id>",
      "destination_root": "D:\\vault\\scratch",
      "interval_seconds": 604800,
      "freshness_seconds": 1209600
    }
  ]
}
```

- `verify` performs the existing repository full read; `snapshot` may pin the
  existence assertion.
- `restore` creates a new timestamped destination under `destination_root/<id>/`.
  It never reuses or overwrites a target.
- Job commands run through the same bounded process runner as the CLI. Password
  material is referenced by file path and is not copied into state.
- The state file records last attempt/success, result, destination, next due,
  missed-run count, consecutive failures and clock anomalies. It contains no
  password or file contents.

## Scheduling

The core is a one-shot `tick`; use the OS scheduler rather than an in-process
daemon. Linux example:

```text
*/15 * * * * /usr/local/bin/peervault schedule-tick --config /etc/peervault/jobs.json --state /var/lib/peervault/state.json
```

Use a dedicated account, a `0700` state directory and an owner-only `0600`
password file. A systemd timer can replace cron; the same owner/lock rules apply.
Windows Task Scheduler should run the same command under one documented task
identity. Do not put the password on the command line.

## Implemented safety behavior

- Duplicate/invalid job IDs, invalid intervals, missing restore roots/snapshots
  and unsupported schema versions are refused.
- State updates are written to a bounded temporary file, synced and renamed.
- On Unix the state file is set to `0600`; Windows owner ACL provisioning remains
  an installer/task responsibility.
- A present lock returns a busy error and is not age-cleared.
- Missed schedules count missed intervals but execute at most once, avoiding a
  catch-up storm.
- A backward clock marks `clock-anomaly` and skips execution.
- `status` distinguishes `unknown`, `fresh`, `stale`, `needs-attention`,
  `clock-anomaly` and `disabled`.
- Job output is bounded by the shared process runner; failures retain a bounded
  sanitized diagnostic.

## Windows desktop

`desktop/PeerVault.Desktop` is a .NET 10 WinForms status/tick shell. Build it with:

```text
dotnet build desktop/PeerVault.Desktop/PeerVault.Desktop.csproj -c Release
```

It starts the core `agent` with inherited stdin/stdout, sends a versioned
`status` or `tick` request and displays the JSON response. It does not edit job
configuration, source policy, history, copy state, recovery instructions or
retention previews yet. The core remains the scheduler/mutation authority. The
agent is killed with the desktop; a closed desktop cannot commit a new job, and
external OS scheduling remains the durable runner.

## Not implemented / not qualified

- No versioned owner-only named-pipe/Unix-socket transport or caller-identity
  check; the current desktop/core channel is inherited stdio only.
- No full desktop operations: source-policy review, history, copy state, recovery
  instructions, conflict inspection and retention preview.
- No Linux service unit, Windows Task Scheduler installer, DPAPI/Credential
  Manager secret delivery or systemd credential integration.
- No quota/free-space preflight, output retention policy, cancellation surface,
  restart reconciliation with a backend journal, or real clock/storage stress.
- Unit tests cover selection/classification/missed/clock logic. They do not prove
  scheduled subprocess success, reboot/suspend behavior, task identity, quota or
  disk-full handling.
- No V0.5 destructive retention/maintenance is used or implied; scheduled
  scratch restores only create new targets.
