# V0.1 — local capture, history, verify and exact restore

Status: experimental implementation on top of the R0-selected restic 0.19.1
adapter. It is not a supported release, sync product or clean-device recovery
path. V0.2 owns clean-device/key recovery; V0.6 owns supported beta qualification.

## Commands

All commands print a schema-v2 JSON report to stdout. The backend executable must
match `backend-lock.json`; a hash or version mismatch refuses the operation.
The repository password comes from `PEERVAULT_PASSWORD` or `--password-file`.
Secrets are never accepted on the command line or written to reports/logs.

```text
peervault init --repository <new-or-empty> --backend <restic>
peervault capture --repository <repo> --backend <restic> --source <tree> [--tag <label>]
peervault history --repository <repo> --backend <restic>
peervault verify --repository <repo> --backend <restic> [--snapshot <id>]
peervault restore --repository <repo> --backend <restic> --snapshot <id> --destination <new-empty>
```

Exit codes: `0` pass, `2` CLI usage, `3` operation/verification failure, `4`
incomplete or empty capture, `130` cancellation. An incomplete capture may have a
backend snapshot but no PeerVault tree oracle; it is not reported as healthy.

## Capture policy

- Portable relative UTF-8 paths, depth ≤ 16, path ≤ 1024 bytes.
- Regular files and directories only. Links, Windows reparse points and special
  files are rejected before capture mutation.
- Case-insensitive duplicate paths are rejected for portable restore.
- File-level consistency only: the source is scanned and hashed before the
  backend capture and scanned again after it. A difference marks the capture
  `incomplete` and skips the oracle; no silent healthy snapshot.
- Empty selection is refused before mutation because the backend cannot commit an
  empty snapshot. An empty file is a valid non-empty selection.
- The manifest records path, size and SHA-256 for every file. It is written to a
  temporary directory and captured as a separate encrypted restic snapshot tagged
  `peervault-manifest-<data-snapshot-id>`.

## Restore contract

- Whole snapshot into a new empty destination only. Existing destinations,
  selective restore, merge, overwrite and resume are rejected.
- The data snapshot is streamed through `restic dump --archive tar` into an
  owned staging directory; PeerVault validates every tar path and type, rejects
  links, traversal, absolute paths, duplicates and unexpected entries, verifies
  size and SHA-256 against the encrypted manifest, then renames staging to the
  destination.
- The restored tree is verified by manifest hash. If the oracle is missing or
  ambiguous, restore refuses instead of claiming a byte-verified result.
- Portable metadata subset: paths, sizes, SHA-256 and the readonly bit. ACLs,
  owners and timestamps are not preserved.
- No proof against a compromised backend that rewrites both data and oracle
  snapshots; the threat matrix records that residual limit.

## Reports

`CaptureReport`, `HistoryReport`, `VerifyReport` and `RestoreReport` use
`schema_version: 2`. `SnapshotRef` records the backend snapshot ID, time,
hostname, paths, tags and the oracle manifest ID when one exists. `RestoreReport`
records `verification: "manifest-hash"`, tree digest, file/directory/byte counts
and the metadata limit.

## Repeatable smoke

```text
python scripts/v01-smoke.py --binary ./target/release/peervault --backend .tools/restic --root .peervault-work-v01-smoke
```

On Windows use `target\release\peervault.exe` and `.tools\restic.exe`. The script
creates a new root, captures two snapshots, restores both exactly, checks the
manifest oracle, rejects an existing destination, refuses an empty selection and
requires a truncated repository to fail verification.

## Observed smoke — 2026-11-01

On Windows/NTFS and Ubuntu 24.04/ext4 (hash-pinned WSL2 image) with restic 0.19.1:

- `init` created a repository-v2 repository on both platforms.
- Two captures (A then B) of 5/6 files including a 5 MiB file, empty file,
  Unicode path, nested/empty directories and readonly file produced data
  snapshots plus encrypted manifest snapshots.
- `history` returned both captures with oracles; `verify` passed repository
  full-read on both platforms.
- Both snapshots restored exactly on both platforms. A Windows restore preserved
  the readonly bit and matched every byte; a second restore to the same
  destination was refused.
- An empty selection was refused with exit 4 before repository mutation; an
  empty file captured and restored normally.
- Ctrl-Break during capture exited 130, withheld backend output and left history
  empty (no committed snapshot).
- A password file worked with `PEERVAULT_PASSWORD` unset; a missing credential
  failed before backend access.
- A truncated copied repository failed `verify` and restore loudly; wrong
  credentials failed without content access.
- Unit tests cover manifest collisions, unsafe paths, symlink/duplicate tar
  entries, traversal, missing files and hash mismatches.

These are local synthetic observations, not production, clean-device, network or
power-loss evidence. The Ubuntu run used virtual same-host storage.

## Not claimed

- Application consistency, VSS, live-file crash consistency or open-file capture.
- Clean-device recovery, separate key custody, rotation or peer replication.
- 5 GiB streamed/50,000-file production corpus and measured time/disk limits.
- Hostile repository containment beyond the validated tar path/type/hash model.
- Index rebuild, disk-full, denied-access and phase-targeted crash qualification.
- PeerVault GC, retention, sync or a PowerShell/desktop surface.
