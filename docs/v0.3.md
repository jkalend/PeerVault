# V0.3 — One authorized peer copy (experimental)

Status: experimental one-peer additive copy with a `PeerCopyRecord v1` state
trail. The tested transport is a local filesystem between two repository roots;
authenticated network transport, pairing, a keyless receiver and independent
hardware remain open. This is not a supported replication product.

## Drill

```text
python scripts/v03-peer-copy.py --binary ./peervault --backend .tools/restic \
  --source-root <new-source-root> --peer-root <new-peer-root> \
  --recovery-root <new-recovery-root>
```

The script:

1. creates and captures a synthetic source repository;
2. initializes a peer repository with its own password;
3. runs the backend-native additive `restic copy` using the source password only
   for the copy;
4. removes the source tree and source repository;
5. lists the peer repository, maps the surviving snapshot by stable capture ID,
   performs a repository full read, and restores exactly into a new target;
6. writes `peer-copy-record.json` with every reached state.

States: `requested` → `transferring` → `transfer-complete` → `source-absent` →
`full-read-verified` → `clean-restored`. Any state can fail; a transfer-complete
record is not a decryption or usability claim.

## PeerCopyRecord v1

The record contains record/capture IDs, source and peer snapshot IDs, the peer
repository ID, oracle manifest ID, transport, key role, additive/no-delete
behavior, source-absence flag, step trail and explicit limitations. It is written
atomically and contains no password or file content.

Observed on 2026-11-01:

| Host | Peer repository | Source removed | Full read | Restore |
|---|---|---|---|---|
| Windows/NTFS, peer G: SATA HDD | distinct repository ID | yes | pass | exact |
| Ubuntu 24.04/ext4 WSL2, peer G: | distinct repository ID | yes | pass | exact |

Both runs are author-only and same-host. The peer held its own repository
password; the source password was used only for the copy.

## Not claimed

- Authenticated network transport, peer identity confirmation, pairing or trust
  removal; the local filesystem is not a transport qualification.
- Keyless receiver operation; the tested peer can decrypt with its own password.
- Independent hardware, offsite location or source-disk removal.
- Interrupted transfer, lost acknowledgement, replaced/absent mount, wrong
  peer/repository, offline peer spanning a capture, or damaged transferred object.
- Remote pruning/deletion; transfers are additive.
- A production `peer-copy` command surface. The drill is orchestration over the
  existing CLI; promotion requires the recorded transport/pairing design and an
  independent security review.

## Required before V0.3 is complete

Choose and test an established authenticated transport/pairing, record the exact
peer/copy repository binding and receiver key role, reconcile interrupted/unknown
transfers against backend state, test absent/replaced mounts and wrong peers, and
perform the clean restore on independent hardware with a second operator.
