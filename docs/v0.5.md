# V0.5 — Retention with backend-native maintenance

Status: owner-executed retention plan, 2026-11-18. Preview is no longer the end
of the slice: `retention apply` revalidates a bound plan under an owner lock and
runs only backend-native `restic forget --prune`. Peer-root pinning, floors,
mass-change pause, state generations and post-execution reconciliation exist.
This is not an independent security review, a remote-peer deletion feature or a
supported release claim.

## Commands

Create the owner state after the first restorable capture:

```text
peervault retention state-init \
  --repository <repo> --backend <restic> --state <state.json> --password-file <secret>
```

Record a peer's last verified recovery root. `--evidence` must be a JSON report
that binds the same peer repository ID, snapshot ID, oracle ID, a completed
clean restore/full read and a verification time within 31 days. The state stores
its SHA-256, not its contents:

```text
peervault retention peer-record \
  --state <state.json> --peer-id <id> \
  --peer-repository-id <64-hex> --snapshot <id> --capture-id <id> \
  --oracle-manifest <id> --key-version <version> --evidence <report.json>
```

Preview and apply:

```text
peervault retention preview \
  --repository <repo> --backend <restic> --policy docs/policies/retention-preview-v1.json \
  --state <state.json> --password-file <secret> > plan.json

peervault retention apply \
  --plan plan.json --backend <restic> --state <state.json> --password-file <secret>
```

`apply` refuses a plan older than 15 minutes, a changed state hash/generation, a
changed repository binding or inventory, a changed peer root, or a changed
decision set. `--ack-mass-change` is required when the preview reports
`triggered` or `unknown`.

After explicit owner review, replace a stale baseline without deleting anything:

```text
peervault retention rebaseline \
  --repository <repo> --backend <restic> --state <state.json> \
  --password-file <secret> --reason "<review note>"
```

Abandon a peer root only after reviewing lost copy coverage:

```text
peervault retention peer-abandon \
  --state <state.json> --peer-id <id> --reason "<coverage decision>"
```

## Policy

```json
{
  "schema_version": 1,
  "keep_last": 1,
  "keep_tagged": [],
  "keep_snapshots": [],
  "minimum_keep": 1,
  "floor_points": 3,
  "floor_days": 30,
  "required_peers": []
}
```

- `keep_last` keeps the newest N **restorable** capture snapshots.
- `keep_tagged` and `keep_snapshots` add explicit pins; an unknown explicit ID is
  a refusal.
- `minimum_keep` adds newest restorable snapshots until the count is met.
- `floor_points` (default 3) retains the newest successful recovery points even
  when policy asks for fewer. If fewer exist, all are retained.
- `floor_days` (default 30) retains every restorable snapshot younger than the
  window. Zero disables the age floor.
- `required_peers` names peers whose latest `last-good` root must exist in state
  and remain retained. A missing, abandoned or deleted root refuses the preview.
- Snapshots without a PeerVault oracle are `protected`, never consume keep slots
  and are never delete candidates.
- Deleting a capture also forgets its encrypted oracle manifest snapshot, so the
  pair does not accumulate. The raw post-condition is one data snapshot and one
  manifest snapshot per retained capture.

Snapshot times are ordered as RFC3339 instants, not timestamp text.

## Execution safety

- The state file is versioned JSON with a monotonic generation, the repository
  canonical path and `restic cat config` repository ID, the last validated tree
  baseline, peer roots and a bounded 64-entry execution history.
- The state must live outside the repository and is written by fsync + atomic
  rename. On Unix it is `0600`.
- An OS-owned file lock (`fs2`) serializes state mutation. Process death releases
  ownership; there is no age-based stale-lock clearing.
- The plan binds policy bytes, state bytes, generation, inventory digest, backend
  version/executable hash and repository ID.
- The mass-change guard diffs the newest and baseline encrypted tree manifests.
  It pauses when at least 20 files **and** 20% of files changed/deleted, or at
  least 25% of bytes changed/deleted. An absent/empty baseline or missing oracle
  is `unknown` and also pauses. Acknowledging a pause is an explicit apply flag
  on the exact previewed plan, not a policy default.
- Deletion is `restic forget --prune <capture-id> <manifest-id>...`; PeerVault
  never unlinks backend objects or runs an object collector. Any backend failure
  is reconciled: removed IDs are recorded as `partial`, an unlistable repository
  as `unknown`, and the state generation advances so the same plan cannot replay.
- After success the state re-lists raw snapshots, checks every kept capture and
  oracle still exists, checks every forgotten ID is gone, and records the newest
  restorable tree as the next baseline. A failed baseline makes the next preview
  `unknown` rather than silently broadening deletion.

## Observed drill — 2026-11-18

`scripts/v05-retention.py` on Windows/NTFS with pinned restic 0.19.1 and the
debug build:

- four captures; one peer root pinned to the second-newest;
- preview kept 2 (newest + peer root), deleted 2 captures and 2 oracle manifests;
- apply passed, state generation advanced, stale plan replay refused;
- kept snapshot restored exactly after maintenance;
- a 100% blob rewrite produced `mass_change: triggered`; apply without
  `--ack-mass-change` refused, with it passed;
- a required peer without a recorded root refused the preview;
- no repository secret appeared in plan or state bytes.

The drill is same-host, author-run and synthetic. It does not prove independent
security review, crash-at-every-phase behavior, concurrent capture/restore,
disk-full handling or clock/listing anomalies.

## Not claimed

- No independent security checkpoint or critical/high deletion finding review.
- No concurrent capture/restore/transfer fault injection; the lock prevents
  PeerVault state writers, but backend maintenance uses restic's own lock.
- No disk-full, kill-at-each-phase or power-loss matrix for apply.
- No peer-repository deletion, tombstone expiry or remote pruning.
- No key-version availability check beyond the recorded reference and explicit
  owner abandonment; a lost key remains needs-attention.
- No claim that `restic prune` finishes within one bounded observation window for
  every repository size.
