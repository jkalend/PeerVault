# V0.5 — Retention preview (no deletion)

Status: experimental read-only retention preview. There is **no PeerVault GC or
delete command**. Nothing in this slice mutates the repository, and a delete
candidate is not permission to delete.

## Command

```text
peervault retention-preview --repository <repo> --backend <restic> --policy <policy.json> [--password-file <path>]
```

Example policy:

```json
{
  "schema_version": 1,
  "keep_last": 1,
  "keep_tagged": [],
  "keep_snapshots": [],
  "minimum_keep": 1
}
```

Example files are in `docs/policies/`. Reports use `RetentionPlan` schema v1 with
`apply: false`; exit `0` is a preview, `3` is an operation/verification refusal.

## Selection

- `keep_last` keeps the newest N capture snapshots.
- `keep_tagged` keeps snapshots carrying any listed exact tag.
- `keep_snapshots` keeps explicit IDs; an unknown ID is a refusal.
- `minimum_keep` adds the newest snapshots until at least that many are kept.
- Snapshots without a PeerVault oracle are listed under `protected` and are never
  delete candidates.
- Remaining snapshots are `delete_candidates` eligible only after a separately
  qualified retention/maintenance gate.

## Observed preview — 2026-11-01

On a V0.1 repository with two captures and `keep_last: 1`:

- one snapshot was kept (`keep-last`);
- one was listed as a delete candidate;
- `history` still returned both snapshots after the preview;
- no backend maintenance or delete command ran.

## Not claimed

- Active capture/restore/transfer locks, peer roots, recovery pins and key
  versions are not evaluated; this is not a safe deletion plan yet.
- No deletion, backend prune/forget, maintenance, remote copy or space reclaim.
- No retention policy application, crash-safety, lock reconciliation or
  retention evidence bundle.
- The first slice has no PeerVault GC command; deletion remains a later reviewed
  capability with its own gate.
