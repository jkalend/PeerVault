# Experimental R0 harness

This is a synthetic local baseline, not complete R0 qualification or a production
backup interface. The backend/profile selection is recorded in
[ADR 0001](adr/0001-r0-backend-selection.md); its open residuals still block a
production release claim. Follow [the catch-up plan](implementation-catch-up.md):
CP0/CP1 repair the entry artifacts and harness; CP2 still blocks production V0.1. Full 1.0 retains opt-in sync; supported backup-only 0.9 can ship
independently once its narrower security/recovery/release gates pass.

The `copy-drill` command adds the CP2 copy/recovery topology probe: it captures
synthetic snapshots into a source repository, copies them with the candidate's
native path to a separately observed physical device, removes the source tree and
source repository, then verifies and restores through a fresh receiver profile.
It is a same-host media-separation and source-absence simulation, not clean-device,
network-transport, keyless-peer or power-loss evidence.

## Run and independently verify the fixture

Rust is pinned in `rust-toolchain.toml`; Python 3.10+ is used for developer tools.
The CLI consumes the public Components workspace as a path dependency at the
commit recorded in `components-lock.txt`. A fresh checkout needs that workspace
before Cargo can resolve `bailiff`:

```powershell
git clone https://github.com/jkalend/Components.git ../../Components
$commit = (Get-Content components-lock.txt -Raw).Trim()
git -C ../../Components checkout --detach $commit
```

On other shells use the file's content as the `git checkout` argument. An
existing checkout must contain the same commit; CI verifies that pin.

```text
cargo fmt --check
cargo clippy --locked --all-targets -- -D warnings
cargo test --locked
python -m unittest discover -s scripts -p test_*.py
python scripts/install-backends.py
cargo build --release --locked
```

From PowerShell, using new disposable directories:

```powershell
.\target\release\peervault.exe fixture .peervault-work-fixture-a
python scripts/check-fixture.py .peervault-work-fixture-a/source --revision 1
.\target\release\peervault.exe fixture .peervault-work-fixture-b --revision 2
python scripts/check-fixture.py .peervault-work-fixture-b/source --revision 2
.\target\release\peervault.exe bakeoff restic --executable .tools/restic.exe --work-dir .peervault-work-restic --profile docs/profiles/windows11-workstation-smoke.json
.\target\release\peervault.exe bakeoff kopia --executable .tools/kopia.exe --work-dir .peervault-work-kopia --profile docs/profiles/windows11-workstation-smoke.json
.\target\release\peervault.exe copy-drill restic --executable .tools/restic.exe --work-dir C:\peervault-r0-work-restic --copy-dir G:\peervault-r0-copy-restic --recovery-dir F:\peervault-r0-recovery-restic --profile docs/profiles/windows11-copy-smoke.json
.\target\release\peervault.exe copy-drill kopia --executable .tools/kopia.exe --work-dir C:\peervault-r0-work-kopia --copy-dir G:\peervault-r0-copy-kopia --recovery-dir F:\peervault-r0-recovery-kopia --profile docs/profiles/windows11-copy-smoke.json
```

The three drill roots must be new and disjoint. Before any backend launch the
harness observes each root's volume and physical device through PowerShell
`Get-Volume`/`Get-Disk`; a same known device refuses the run, and unavailable
identity requires `--acknowledge-unknown-media` and is retained as unknown
coverage. Storage Spaces or shared controllers can hide residual failure domains;
distinct observed logical devices are not proof of independent hardware.

On Linux use `./target/release/peervault`, `.tools/restic`/`.tools/kopia`, and an
applicable Linux profile. Omit `--profile` for an explicitly unnamed/unqualified
smoke run. Each full bakeoff or drill run needs roughly 2 GiB.

Scored R0 profiles are `docs/profiles/windows11-26200-9168-r0.json` and
`docs/profiles/ubuntu2404-24.04.5-wsl-r0.json`. They require no `missing_fields`
and an observed `clock_probe`; the older `*-smoke.json` profiles remain partial.
The [threat and survival matrix](r0-threat-matrix.md) and
[evidence bundle template](r0-evidence-template.md) are the R0 entry artifacts.
The Ubuntu profile uses a hash-pinned WSL2 image and records virtual storage as a
residual limit, not independent physical media.

Fixture v1's [A](../tests/fixtures/v1-a.json) and [B](../tests/fixtures/v1-b.json)
goldens keep their original bytes. A has 64 files / 268435456 bytes; B has 63 /
264241152 bytes. xorshift64* seed `0x504545525641554c XOR stream_index` uses shifts
right 12, left 25, right 27, multiplier `0x2545f4914f6cdd1d`, little-endian output.
Files 0–2 share stream 0. Sizes: indices 0–59 are 4 MiB, 60–61 are 8 MiB, 62–63
empty. Preserve literal Unicode paths, three directories and readonly source bit.
B inserts 4096 `0xa5` bytes at file-03 offset 4096, drops its final 4096 bytes,
renames file-04 and deletes file-05. The Python checker independently enumerates
and hashes the complete source; backend output never supplies expected hashes.

## Commands and assertions

Report `command_ref` values beginning `r0/` identify these fixed runner commands;
paths, repository passwords and raw backend stderr are never exported.

| Command reference | restic | Kopia |
|---|---|---|
| version-pin | `version` | `--version` |
| init / source-init | `init --repository-version=2` | `repository create filesystem --path <owned-repository> --no-check-for-updates --no-enable-actions` |
| snapshot-a/unchanged/b | `backup --json --host=peervault-fixture .` from owned source | `snapshot create --json --fail-fast --force-hash=100 <owned-source>` |
| history / receiver-history | `snapshots --json` | `snapshot list --json --all` |
| repository-full-read / snapshot-full-read | `check --read-data` (repository) | `snapshot verify --verify-files-percent=100 <snapshot-id>` (attempted snapshot scope) |
| copy-destination-init | initialize an empty destination repository | destination directory is created empty before `sync-to` |
| repository-copy | `copy --from-repo <source> --from-password-file <disposable>` | `repository sync-to filesystem --path <copy>` with default no-delete |
| receiver-repository-full-read / receiver-snapshot-full-read | same full read in the fresh receiver session | same snapshot verify in the fresh receiver session |
| restore-* / receiver-restore-a,b | `restore <id> --target <new-target> --verify` | `snapshot restore <id> <new-target> --no-overwrite-files --no-overwrite-directories --no-overwrite-symlinks` |
| wrong-password | list with wrong secret | fresh-config connect with wrong secret |
| timed-process-interruption | terminate a capture after 100 ms | same |
| fresh-client-connect | cache always disabled | fresh-config/cache `repository connect filesystem` |
| unlock-owned-disposable-repository | `unlock`, this exclusive synthetic repo only | not applicable |
| truncation / bit-flip | damage a disposable data pack, require full-read failure, restore original bytes | same, select the sharded `p/` data-pack directory |

In `copy-drill`, restic assigns new copy snapshot IDs and retains the source ID in
each copied snapshot's `original` field; Kopia `sync-to` preserves snapshot IDs.
The harness requires a one-to-one mapping, removes the source tree and source
repository, then lists, verifies and restores through a receiver session whose
HOME/config/cache are outside the writer root. A byte-for-byte repository
inventory before and after receiver access records missing/changed/added data
objects; only restic `locks/` and Kopia maintenance-format files are classified
ephemeral. No delete command is issued.

Every restored tree must match exact paths/types/sizes/SHA-256 and the sibling
canary must be unchanged. Native extraction accepts only the self-created fixture
repository. This is no sandbox or arbitrary-archive containment qualification.
The deliberate startup kill remains an **unknown mutation outcome**; preserved
old snapshots do not reconcile a possibly committed additional capture. Errors
while a mutation may have happened remain unknown, never implied rollback. The
drill deletes the source only after the copy step returns; it does not claim that
copy health was established before source loss, and it is not a clean-device or
offsite recovery.

## Pins, bounds and failures

`backend-lock.json` v2 is the sole version/archive/executable pin source. The Rust
runner compiles it in, stages the selected binary, verifies the approved extracted
SHA-256 **before any execution**, then checks version output. Rebuild after pin
updates. The installer verifies version/URL agreement, cached/downloaded archive
and extracted-binary digests, member type and bounded decompression before atomic
replacement. Failure leaves the previous executable intact. Binaries remain
external dependencies and are not included in experimental packages.

Keep the 300-second command deadline and 4 MiB per-stream limit. Bounded pipes
replace disk spools: at most the limit plus one sentinel byte is retained per
stream, plus finite OS pipe buffers, with no polling disk overshoot. Windows Job
Objects (kill on close) / Unix process groups own descendants. Limits, cancellation,
normal leader exit and errors terminate the group and reap its direct child.
Ctrl-C/SIGTERM cancellation records evidence and exits 130. A hostile process that
escapes its Unix group or an abrupt parent SIGKILL is not contained by this claim.
RSS, handles and repository disk usage are not yet hard quotas.

The small fixture comparator retains 1 MiB manifest, 1024 entries, depth 16,
1024-byte relative paths and 16 MiB/file limits. Windows work roots are ordinary
local drive paths up to 180 UTF-8 bytes. Symlink/reparse/special paths are rejected.
No metadata, app consistency, live source, >4 GiB or many-file claim is implied.

Experimental `Evidence` v3 records phase/command, assertion/outcome/reason,
versions and binary/pin/source hashes, profile/hash, limits, timings, snapshot IDs,
fixture hashes, restored counts, untested cases and, for `copy-drill`, observed
media identities (hashed), snapshot mapping, copy/delete semantics and repository
inventory summaries. Evidence v2 remains readable; v3 is not silently
reinterpreted as an older schema. `result=pass` means baseline assertions passed;
`gate_status=partial` keeps R0 open. Limit/setup/fault failures produce
fail/unknown evidence even before backend launch. If a work root cannot be safely
created, JSON is emitted to stdout without writing existing data.
It is separate from the planned production RestoreReport v1.

## Evidence retention and remaining gates

```text
python scripts/evidence.py export <work-root> <explicit-registry-root> --profile <exact-profile-input>
python scripts/evidence.py verify <retained-run-directory>
```

Use the planning registry `evidence/peervault/R0/<profile-id>/<run-id>/`.
The explicit exporter inventories only sanitized reports, profiles, input digests,
fixture oracles and command references. Existing runs are never overwritten.
Missing/changed/extra evidence members invalidate verification. Keep raw work
roots, cache, backend config and repositories ignored. Templates and required
threat rows live in the registry; CI artifacts alone expire and do not replace it.
Recorded SHA-256 identifies bytes, not truth, authority or recoverability.

CP2 now has local `copy-drill` baselines for both candidates: native copy to a
separately observed device, one-to-one snapshot mapping, source-tree/source-repository
removal, receiver full read and exact restores without non-ephemeral repository
changes. Those runs remain partial. CP2 still requires scored exact Windows 11 and
Ubuntu 24.04 profiles; a supported network/keyless/clean-device topology with
separately held secrets; safe production export/contained writes; observed-phase
crash/index/access/disk-full/metadata faults; clock/storage stress and an explicit
backend decision. Process kills are not power-loss evidence. Storage Spaces and
shared controllers can hide residual failure domains even when logical device
identities differ. No backend selection, production adapter, remote copy, pruning,
sync or release approval follows from these smoke runs.
